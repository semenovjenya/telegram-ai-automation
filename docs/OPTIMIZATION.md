# Оптимизация Telegram AI Automation

## Измерение окна истории

`ai_brain/nodes/agent_runtime.py` ограничивает предыдущую историю 30 сообщениями и исключает повтор текущего вопроса, который memory node уже сохранил до запуска агента.

Benchmark использует реальный `build_messages`, фиксированные синтетические сообщения и одинаковую сериализацию `role/content` для обеих сторон. Baseline — всё полученное окно истории и один экземпляр текущего вопроса. Это сравнение действующего лимита с неограниченной передачей окна, а не измерение старой production-версии.

```bash
python -m benchmarks.context_budget
```

| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 12 / 12 | 2915 | 2915 | 0% | 0 |
| 50 | 52 / 32 | 14055 | 8485 | 39,63% | 20 |

Размер измеряется в UTF-8 байтах JSON. Токены, цена, latency и качество ответа не измерялись. Исключение сообщений является **потерей старого контекста**, поэтому эти цифры нельзя называть сжатием без потерь. Ограничение числа сообщений не устанавливает общий лимит символов для произвольно длинной истории.

## Router без LLM-вызова

`router_node.py` детерминированно выбирает `GENERAL`, `SALES` или `BARTER`. Он читает текущий вопрос и последние четыре сообщения, не инициализирует модель. Это устраняет отдельный модельный вызов на routing по сравнению с дизайном, где intent определяется LLM; денежная экономия не замерялась.

Компромисс: ключевые слова и недавняя история могут перехватывать неподходящий intent. Такой router удобен для ограниченного набора сценариев, но требует regression cases при расширении продукта.

## Ограниченный retrieval

`ChannelSearchClient` принимает `top_k` от 1 до 20 и обрезает число результатов до запрошенного значения. Форматирование дополнительно ограничивает число фрагментов пятью, текст одного фрагмента — 1 200 символами, source — 200, общий контекст — 6 000.

Sales запрашивает три результата; поиск каналов использует другой профиль. Это предсказуемый бюджет контекста, но отсечение может убрать релевантный факт. Обработка неполных ответов не заменяет оценку retrieval quality.

## Tool outputs и генерация

Barter tools возвращаются модели как `UNTRUSTED_TOOL_DATA` с JSON-envelope и флагом `truncated`. В envelope попадает до 6 000 символов исходного результата; служебная оболочка добавляет собственный размер. Инструкция о недоверенных данных снижает смешение данных и управляющего текста, но сама по себе не доказывает защиту от prompt injection.

Chat model ограничивает output tokens настройкой `MAX_OUTPUT_TOKENS`, имеет timeout 45 секунд и до двух retries. Timeout и retries ограничивают отдельные вызовы, а не гарантируют фиксированную длительность всего workflow.

## PostgreSQL и event loop

История использует connection pool. Memory nodes вызывают синхронные операции БД через `asyncio.to_thread`, чтобы не блокировать event loop. Pool limits и ограничение числа возвращаемых сообщений помогают контролировать ресурсы; они не являются доказательством throughput или нагрузочного SLA.

## Что ещё измерять

Для live-оценки нужны сравнимые запросы, один dataset, одинаковая модель и учёт input/output tokens, latency p50/p95, ошибок intent и пропущенных фактов. Ни синтетический benchmark, ни количество unit-тестов не подтверждают экономический эффект на реальных диалогах.
