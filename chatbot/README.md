# Telegram adapter boundary

The original `chatbot` directory was an unpublished nested repository. It is
not required by the public core stack anymore.

The platform talks to a Telegram adapter over HTTP. For a clone-and-run demo,
Compose starts the read-only implementation in `compose/telegram-mock`. A live
adapter is an external integration and must expose the same endpoints:

- `GET /health`
- `POST /api/channel-search`
- `GET /api/channels/{username}`
- `GET /api/chats`
- `GET /api/chats/{chat_id}/messages`
- `POST /api/chats/{chat_id}/messages`

The message POST accepts exactly one JSON field:

```json
{"text": "Message text"}
```

User content must never be placed in query parameters or access-log URLs. The
gateway and adapter reject query parameters on this route, require
`Content-Type: application/json`, and bound the text length. Request bodies and
query strings must be redacted from application, proxy, and ingress logs.

Point the platform at a live adapter with `TELEGRAM_ADAPTER_URL`. Credentials,
session files, and message-sending operations intentionally stay outside this
public repository.

## Authentication and tenant contract

Every `/api/...` adapter endpoint requires the service credential in
`X-API-Key`; `/health` remains an unauthenticated liveness probe.
`POST /api/channel-search` and `GET /api/channels/{username}` use only this
service boundary because their data is shared.

The tenant-scoped chat endpoints additionally require four headers generated by
the authenticated gateway:

- `X-Tenant-Claim-Version: 2`
- `X-Tenant-ID: <positive saas_user_id>`
- `X-Tenant-Timestamp: <Unix time in nanoseconds>`
- `X-Tenant-Body-SHA256: <lowercase SHA-256 hex of the exact HTTP body>`
- `X-Tenant-Signature: <lowercase HMAC-SHA256 hex digest>`

The signing key is a separate secret, `TELEGRAM_TENANT_SIGNING_KEY`; it must not
be the JWT secret or the Telegram API key. The canonical signed bytes are UTF-8:

```text
v2\n{tenant_id}\n{timestamp_ns}\n{UPPERCASE_METHOD}\n{canonical_relative_path}\n{body_sha256}
```

For example, the path is `api/chats` or
`api/chats/{chat_id}/messages`, without a leading slash. A live adapter must
verify the API key and HMAC, bind the signature to the exact method and path,
compare the body digest against the exact received bytes before parsing or
acting, reject expired or future claims, and consume each accepted signature
once to reject replay. GET uses the SHA-256 digest of an empty body. Replay
storage must be bounded and fail closed when full.
Caller-provided tenant headers are untrusted; the gateway strips them before
creating its own signed claim from the verified JWT.

Mutating Telegram operations remain outside the public demo. A live adapter
must put them behind a separate, explicit user-confirmation policy in addition
to the authentication and tenant checks above. The synthetic adapter validates
the POST contract but always returns `405 Read-only demo adapter`.
